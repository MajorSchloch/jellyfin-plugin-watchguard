# v0.7.10 native ordering qualification correction

The release qualification at master `c8f030e6b880bd8f96ce8ed4861f357e552cd1a3` failed in [12.4 / activity-native](https://github.com/MajorSchloch/jellyfin-plugin-watchguard/actions/runs/40847683501/job/123359607051), scenario `single-recent`. Artifact `12885824760` records the assertion and candidate DLL hash but does not contain the returned rows. The exact offending pair cannot be recovered from that artifact.

The Python comparison oracle used serialized timestamps for both each title's maximum owner date and descending title order. For example, `.1Z` sorts lexically after `.11Z`, although 100 ms precedes 110 ms. Equivalent offsets and trailing-zero precision also invalidate string ordering. The runtime's `BrowserQuery.Sort` already compares nullable UTC ticks.

The corrected oracle parses explicit `Z` or signed `HH:MM` offsets into integer UTC ticks since 0001-01-01, retaining all seven fractional digits (100 ns). Missing/null dates remain unknown and sort last. Ambiguous, invalid or out-of-range timestamps fail rather than silently becoming unknown. Status filtering still precedes date aggregation; existing title/ID tie-breaks remain unchanged. No plugin runtime, activity-query, pagination, limits or retry changes are included.

Every comparison sample now writes an allowlisted `order-<candidate>-<scenario>-<sample>.json` before checking ordering, membership, owners or reasons. It contains the scenario/query/sample, actual and expected IDs, raw owner dates, normalized UTC ticks, title tie-breaks and expected aggregate date keys. API envelopes, credentials and continuation tokens are excluded. These files travel with the existing activity-native failure artifacts; their number is bounded by the existing six scenarios and four samples for each candidate.

Ten focused tests cover fractional precision, whole seconds, 100 ns precision, equivalent and differing offsets, null/missing dates, multi-owner maxima for both date fields, status-scoped aggregation, title/ID ties, invalid input, and rejection of genuinely wrong order with evidence already on disk. Existing strict membership, owner, reason, permission and no-background-reclassification assertions remain in place.

## Follow-up: native cancellation dismissal

The remaining failure is a race between the test's next navigation and native dialog/history teardown. In artifact `12889765679`, “Got It” completes at trace time 12809.425 ms; a frame at 12861.784 ms still shows the native error dialog. The test starts its programmatic details navigation at 12950.987 ms, and the details heading subsequently times out over a blank content area. [Original trace timings and pinned fixture identity](evidence/native-ordering-v0710/dialog-dismissal/original-race.json), [closing dialog](evidence/native-ordering-v0710/dialog-dismissal/before-navigation-dialog-closing.jpeg), [navigation during dismissal](evidence/native-ordering-v0710/dialog-dismissal/navigation-during-dismissal.jpeg), [blank content](evidence/native-ordering-v0710/dialog-dismissal/after-navigation-blank.jpeg).

The pinned 12.3 Web `dialogHelper` confirms that clicking a dialog button starts an exit animation. Its `_close` handler removes the dialog and performs native history-back handling; only after the history notification does it emit `close`. This is why click completion alone is not readiness for another programmatic route change. The existing general cancellation helper already waits for the error text to become hidden; the playback-only series path omitted that wait.

The playback-only path now registers a native `close` listener before clicking “Got It,” awaits completion and hidden error text, and requires the existing series heading and native More button to be visible before continuing. It clears the canceled deletion's pending-success redirect marker. The next movie's visible heading and More-button assertions, zero-DELETE cancellation checks, existence checks and historical packages are unchanged. Three focused tests cover hidden text with history teardown still pending, immediate close during the click, and propagation of a missing-close failure without retries. Native reports record the observed close/view/navigation sequence.

The fresh unchanged 12.3/published-v0.3.1 run passed the complete historical sequence; this is an intermittent race rather than a deterministic failure on every run. The failing CI frames and native lifecycle establish the missing synchronization. No real visible-control interaction failure was observed in the local baseline; the problematic next step is the test's programmatic `page.goto`, which can start while a native modal is closing. No sleeps, longer timeouts, reload recovery or retries are introduced. The [corrected native 12.3 run](evidence/native-ordering-v0710/dialog-dismissal/local-corrected.json) passed the complete historical browser suite with zero ordering violations. It observed `closedWhenClickReturned=false`: native close occurred 149.4 ms after the post-click measurement, the series view was ready afterward, and only then did the next movie navigation begin and pass its visible controls checks. This reproduces the pending-teardown condition without adding artificial delays. Fast checks passed (376 backend, 202 JavaScript, 47 Python and eight catalog tests); packaging retains the exact ZIP/DLL hashes above. Full qualification is pending.
