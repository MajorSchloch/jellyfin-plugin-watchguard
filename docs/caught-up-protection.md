# Caught Up protection — v0.4.3

`ProtectCaughtUpSeries` defaults to **true** and is exposed on Dashboard → Plugins → WatchGuard. Existing configuration XML without this property receives the default; explicit false remains false. Saving applies to the next protection request without restarting. Activity window/limit, diagnostics, personal preferences and both JSON schemas are unchanged.

The existing administrator-authorized `GET /WatchGuard/Protection/{id}` keeps its response shape. For a series it performs a fresh targeted batch evaluation and may add the `CaughtUp` reason. It never consumes the informational endpoint's HTTP result, global candidate discovery or cached activity. Episode and season deletion continue to resolve their verified parent series through the existing adapter; no additional deletion-path network request is added.

CaughtUp protects only a Continuing series with at least one eligible aired episode, all such episodes watched and sufficient native episode/air-date coverage. Ended watched history, unknown status and incomplete metadata do not become CaughtUp. Watchlisted, unfinished available playback and CurrentlyPlaying remain independent protection reasons, including the requester's own interest. Existing unfinished available playback protection is preserved even for an available future episode; informational aired progress is separate.

A metadata gap is an explicit unknown classification, not affirmative CaughtUp. With protection enabled, a continuing series with observed viewing activity but incomplete coverage also returns 503 instead of approving deletion from that incomplete classification. Resolve its native metadata or explicitly disable only Caught Up protection if appropriate; other reasons remain protected. A native lookup/storage/batch failure or safety-limit exhaustion makes protection return 503: the adapter refuses deletion. It never treats a truncated list as confirmed zero interest. Disabling the setting removes only CaughtUp as a protection reason and does not disable safety checks or other interest reasons.

The structured dialog now accepts Caught Up alongside existing reasons. For your own interest it says “You are caught up and waiting for new episodes.” Native confirmation still appears first. Cancel, Escape, close, identity changes and failed/malformed lookups send no DELETE. Explicit approval calls the original native method exactly once, preserving arguments, receiver, return/rejection behavior and native permissions. Jellyfin's generic cancellation error remains. There is no server-side deletion bypass and no protection for direct API, native-client or filesystem deletions.

## Upgrade from v0.4.2 and rollback

Back up `Jellyfin.Plugin.WatchGuard/watchlists.json`, `preferences.json` and `configurations/Jellyfin.Plugin.WatchGuard.xml` under the actual plugin data root. On LinuxServer.io this is normally `/config/data/plugins`. Stop writes or stop Jellyfin for a consistent backup. Do not put these files in versioned assembly folders.

After release approval/publication, use the normal catalog update, restart, confirm a single active WatchGuard assembly, and fully reload every Web tab. No Injector, environment flag, Web-file edit or schema migration is required. Verify the enabled setting and test Cancel on disposable Caught Up media before relying on the changed behavior. A retained v0.4.2 browser adapter cannot interpret CaughtUp and fails closed on that reason; stale tabs must still be reloaded.

For rollback, preserve the immutable published v0.4.2 ZIP and restore that single catalog version, restart and fully reload clients. Existing watchlists/preferences are compatible; v0.4.2 ignores the added XML property but can drop it if saving configuration. Re-upgrading without the property enables the new default again. Rollback restores v0.4.2 semantics: Caught Up alone does not warn. Keep the configuration backup if you need to retain an explicit false setting.
