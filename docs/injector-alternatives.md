# Future single-plugin installation: research only

v0.3.1 **retains JavaScript Injector**. No alternative loader, middleware, Web-file rewrite or File Transformation dependency is implemented. Research targets the pinned Jellyfin Server/Web 12.2 sources used throughout this repository.

## Supported building blocks

1. **Native plugin Web pages.** `IHasWebPages` and embedded resources work for dashboard configuration. `DashboardController` serves those pages and Web's plugin configuration route loads their HTML/JavaScript. This is appropriate for settings, but visiting a plugin page is not a global bootstrap for every Web session. It cannot guarantee pre-delete warnings on native detail/library routes.
2. **Service registration and middleware.** `IPluginServiceRegistrator.RegisterServices` is Jellyfin's native DI extension. ASP.NET Core's `IStartupFilter` is a supported host startup mechanism and can be registered through DI. The current Injector uses this combination successfully on 12.2. Jellyfin does not offer a dedicated supported HTML/script-injection hook or contract for middleware ordering around the bundled Web entry point.
3. **Custom assets.** A discovered plugin controller can serve embedded JavaScript/resources with appropriate content type and authentication/cache policy. Native embedded dashboard pages also serve assets. Serving a URL does not make the static Web bundle load it; a bootstrap/inclusion mechanism is still required.

## Static bundle and response rewriting

[Server Startup](https://github.com/jellyfin/jellyfin/blob/ca0f16eb7c195f720a1493ed469a27c4657db0c6/Jellyfin.Server/Startup.cs) mounts static Web files and response compression. The [Web router](https://github.com/jellyfin/jellyfin-web/blob/61b1f890365ad15138e943e694af723c1d47df2a/src/RootAppRouter.tsx) imports its routes statically. Neither provides runtime plugin bootstrap registration. Dashboard-page capability does not imply a hook into these routes.

A response-time loader could theoretically live inside WatchGuard through an `IStartupFilter`, while leaving Web files unchanged. It would need tightly bounded handling of the actual index response, base URLs, GET versus HEAD, encoding/compression, content length, cache validators/304s, range requests, failures, middleware ordering, reverse proxies, duplicate loader markers, authentication changes and multi-server client behavior. CSP imposed by the server/proxy/browser must permit the chosen loader and assets; same-origin external assets reduce inline-script concerns but do not override a restrictive policy. Do not weaken CSP or assume configuration from one deployment applies to another. Asset delivery also does not make the existing version-specific UI hooks a supported Jellyfin API.

The existing Injector [startup filter](https://github.com/n00bcodr/Jellyfin-JavaScript-Injector/blob/2758804c987d490ef32fc2fbdb8a73a44facdf2c/Jellyfin.Plugin.JavaScriptInjector/Services/ScriptInjectionStartupFilter.cs) demonstrates several of these concerns, including uncompressed complete responses and validator handling. Its code is **GPL-3.0** at the inspected revision; adopting source requires preserving applicable notices/license and meeting corresponding-source/distribution obligations. WatchGuard already carries GPL licensing, but that does not remove attribution obligations or establish that copying a whole implementation is minimal. No Injector implementation was copied for this release.

## Recommendation

Keep the tested dependency in v0.3.1. The smallest supported improvement would be an upstream Jellyfin global plugin-Web bootstrap extension; none was found in the inspected 12.2 sources. Pending such an API, a narrowly scoped, independently reviewed response-time loader inside WatchGuard is a technically feasible **maintenance commitment**, not a fully supported Jellyfin Web integration. Evaluate it in a separate disposable proof of concept, with explicit ownership of HTTP edge cases and a full browser/proxy/CSP regression matrix. Removing one installation dependency would transfer its maintenance burden into WatchGuard. Do not automatically proceed based on this research.
