# Capability-based compatibility: proposal, not enabled

This document describes a possible future policy. The drawer/qualification change does **not** alter version gating, catalog ABI, dependency versions or deletion protection. WatchGuard still explicitly accepts Jellyfin Server/Web 12.2.0 and 12.3.0 and requires the existing structural checks. Unknown versions remain unsupported.

## Current boundaries

The package targets .NET 10 and references the Jellyfin 12.2.0 controller/model APIs. Its minimum catalog ABI is 12.2.0.0. A catalog minimum is an installation floor, not a promise that every later server can load the assembly or preserve behavior. Missing types, methods, constructors, service registrations or incompatible signatures can prevent plugin startup before a capability probe runs. A Web compatibility result also cannot prove server enforcement compatibility.

`ServerEnforcement/Registration.cs` recognizes the native `Jellyfin.Api.Controllers.LibraryController`, both `DeleteItem(Guid itemId)` and `DeleteItems(Guid[] ids)` actions returning `ActionResult`, and their HTTP DELETE route templates. The exact-version test is additional to these checks. The startup attachment report requires both filters and captured configuration before claiming support. Native-fixture qualification separately checks packaged signatures, authorization and bulk binding and exercises real deletion/approval behavior.

If the convention cannot recognize the endpoints, it attaches no filters and reports unsupported. **This is not a server-wide fail-closed barrier:** native deletion routes may remain usable without WatchGuard enforcement. If an attached, enabled guard finds unsupported state or cannot evaluate protection, it rejects that intercepted operation (503 for unsupported/unavailable protection); it does not call the native action. Explicitly disabled enforcement delegates to native behavior. Those cases must remain distinct in reporting. Browser interception and authoritative Protection are not substitutes for server-side attachment; other deletion mechanisms and direct filesystem access are outside this HTTP guard's scope.

## Proposed progression

1. Keep a bounded ABI envelope. A compatible assembly-load/runtime/API family is a prerequisite; major or otherwise ABI-breaking changes require an adapted build and, where necessary, a higher catalog floor. Retain the 12.2 floor only while the same package is demonstrated to work there. Do not turn an open-ended minimum ABI into an open-ended support claim.
2. Define separate server and Web capabilities. Server checks should inventory every protected native deletion route, parameter binding, authorization/filter ordering and service dependencies, then verify that all intended endpoints actually carry the guard. Existing structural checks remain mandatory. Web checks should cover authenticated API availability, loader/base-path/CSP behavior, route/history contracts and recognized layout slots. A missing optional drawer slot should disable that UI integration without changing deletion policy.
3. Distinguish **recognized**, **attached**, **qualified** and **enabled**. A runtime shape match proves less than behavioral qualification. Publish exact tested Server/Web/image versions and artifact checksums, with the two-host workflow testing one package. Initially use new probes only for diagnostics alongside the allowlist. Exercise intentionally changed signatures, binders, missing endpoints and permission semantics in negative fixtures before considering a broader supported envelope.
4. Decide unknown-host deletion behavior explicitly in a separate security change. A future policy must not silently report protection when a newly added deletion route bypasses the guard. Options include refusing startup when enforcement is requested but complete interception cannot be established, or a narrowly scoped deny barrier covering an independently verified native deletion surface. Either option needs administrator recovery, disabled-mode semantics, tests for new/renamed routes, and an explicit decision about service availability. Attaching to a guessed endpoint or blocking all HTTP requests is not an acceptable fallback.
5. Only then replace exact-version gating with a bounded, reviewed capability policy. Demonstrate identical protection, authorization, approval single-use/revalidation, work limits and native continuation behavior on every accepted host. Changes to authoritative Protection, storage and approvals require their own review; a freshness or compatibility revision cannot replace live authorization.

No probe can prove future semantic compatibility from reflection alone. Retain a qualified-version list even if a later policy accepts a wider capability-compatible range, and make any unqualified status visible without claiming protection that has not attached.
